# ARCHITECTURE

This page explains to a newcomer what Second Brain is and how its pieces fit together, so that the other pages of this documentation make sense.

## What Second Brain is

Second Brain is a durable memory and a cross-project operating system for working with AI agents: rules, methods, templates, skills and automatic guardians, versioned in a single Git repository that you own ([README.md](../../README.md)). The files remain the source of truth; the tools revolve around them.

You need a paid subscription to at least one AI agent (Claude Pro or higher, or ChatGPT Plus or higher). Nothing is designed or tested for a free account ([INSTALL.md](../../INSTALL.md)).

« Vault » and « Second Brain » are the same thing: « Vault » is the internal name used in the rules and the tools, « Second Brain » is the name you see ([CONTEXT.md](../../CONTEXT.md)).

## The pieces

### The Vault

The Vault is this repository. Once installed, your clone is called `second-brain`. It holds what is cross-cutting: rules (`rules/`), recorded Decisions (`decisions/`), templates (`templates/`), the method's skills (`skills/`), the library of verified third-party skills (`skills-warehouse/`) and the shared tooling (`tools/`). It also holds your profile, `USER.md`, and the identity of your Vault, `VAULT-IDENTITY.md`.

The identity file is generated once, at installation, by `tools/vault-identity.sh`. Its `vault_id` is copied into the birth certificate of each project, so a project can check that it talks to the right Vault ([VAULT-IDENTITY.md](../../VAULT-IDENTITY.md)).

### The workspace

The workspace is the folder that contains `second-brain` and your projects. It is marked by a file at its root, `<workspace>/VAULT-ROOT.md` ([CONTEXT.md](../../CONTEXT.md)). Any agent working inside a project walks up the parent folders until it finds this marker, the same way Git finds a repository by its `.git` folder ([vault-root-template.md](../../templates/vault-root-template.md)).

The marker is generated by `tools/write-marker.sh` and must not be edited by hand. It gives three facts: the relative path of the Vault from the workspace root, the identity of the Vault, and its origin. It resolves on its own only when there is a single candidate Vault in the workspace; otherwise a project names its Vault through its birth certificate.

A typical workspace looks like this (the project name is an example):

```text
<workspace>/
├── VAULT-ROOT.md              marker: where the Vault is, its identity, its origin
├── CLAUDE.md, AGENTS.md       ten lines at most, set up by the installer
├── second-brain/              the Vault (this repository)
│   ├── rules/  decisions/  templates/  tools/
│   ├── skills/  skills-warehouse/
│   ├── projects/PROJECT-REGISTRY.md
│   ├── USER.md  VAULT-IDENTITY.md  CONTEXT.md
│   └── .install/state.json    installation logbook, never tracked by Git
└── my-project/                a project next to the Vault
    ├── .pre-commit-config.yaml    birth certificate at its head
    ├── state/PILOT-PROMPT.md      the project's Pilot prompt
    ├── state/STATE.md             the generated state sheet
    └── .claude/  .agents/         links to the assistant and the skills
```

Nothing else belongs at the root of the workspace: besides the marker and its two guides, the Vault and your projects (or the group folders that hold them), only the organs the marker declares, `_trash`, `_archive` and `_orders`, where the welcome Pilot leaves initiation orders. `tools/check-workspace-root.sh` compares the root with that list at every Executor opening, as a warning, never a block. The tools' throwaway files go to one declared temporary folder **outside** the workspace, named in the marker ([rule on workspace hygiene, project names and session types](../../rules/RULES-2026-09-26-112218-workspace-hygiene-project-names-session-types.md)).

### Projects

A project is a work folder next to `second-brain`, entered in the registry (`projects/PROJECT-REGISTRY.md`), which inherits the method ([CONTEXT.md](../../CONTEXT.md)). The installer can create your first project; an existing folder, with or without Git, becomes a project through `tools/project-bootstrap.sh` in its `adopt` mode, without anything it contains being modified ([README.md](../../README.md)).

Adoption writes a **birth certificate** at the head of `<project>/.pre-commit-config.yaml`: the identity of the Second Brain that adopted it, the commit, and the `vcs`. A project attaches to its Second Brain through this certificate, never by proximity. Each project also carries its Pilot prompt, `<project>/state/PILOT-PROMPT.md`, generated at its creation.

The boundary is strict: you use Second Brain **from** your projects, and you make it evolve **in** `second-brain` itself, through a Mission. A project never writes into `second-brain`; only a genuinely generalizable improvement rises into it ([boundary rule](../../rules/RULES-2026-09-11-190000-project-second-brain-boundary.md)).

### The assistant

The assistant is Second Brain's agent. You name it at installation; the default proposed name is « Brian ». It guides the installation, then answers read-only ([CONTEXT.md](../../CONTEXT.md)). The installer generates it as a Claude Code subagent, a Codex skill, and a web package that you upload yourself into a claude.ai or ChatGPT Project. The subagent and the skill are linked into each project, never into your user profile ([README.md](../../README.md)).

### The MCP server

The Pilot works in **the Claude desktop application**, and that is where Second Brain's MCP server lives. It gives the Pilot disk access bounded to your workspace. It does not exist in the browser. There is one server per Vault, named `second-brain-vault-<workspace>` after the workspace folder (for example `second-brain-vault-workspaces`), so two Second Brains on one machine keep two servers side by side ([README.md](../../README.md)).

The server is set up by `sb install --mcp` in a terminal, by `/first-install` from Claude Code or Codex, or by hand with the installer script ([install-vault-mcp.sh](../../tools/install-vault-mcp.sh)), which takes the workspace folder as its argument. The authorized folder is the root of the workspace; after it runs, you restart the application. `tools/check-mcp-containment.sh` checks the configuration written on disk, and the Pilot's first answer carries a **canary**, the proof that it read the disk through this server rather than from memory ([INSTALL.md](../../INSTALL.md)).

### The sb command

Every operation of Second Brain has one English verb of one command, `sb` — `sb open`, `sb close`, `sb new`, `sb update`, `sb doctor`, 22 verbs in all. `sb` is a program of the Vault (`tools/sb/sb.py`) that works without any model; each verb checks where it runs, then calls a tool, a skill or a guide that already exists, and never decides anything itself. The surfaces relay it rather than duplicate it: `sb <verb>` in a terminal, `/sb:<verb>` in Claude Code through the plugin `sb`, `$sb <verb>` in Codex through one router skill, and a message that starts with `sb ` to the Pilot, which applies the verbs that need no shell ([rule on the sb command surface](../../rules/RULES-2026-09-26-200933-sb-command-surface.md); [Use the sb command and its plugin](../how-to/use-the-sb-command-and-plugin.md)).

## Who does what: Owner, Pilot, Executor

You are the **Owner**: you decide and you push. Every work session holds a single role, either **Pilot** or **Executor** ([role charter](../../rules/RULES-2026-08-23-224706-role-charter-and-session-determination.md)). The Pilot thinks, arbitrates with you and drafts the Missions, without executing: no shell, no `git add`, commit or push, and file access only through the MCP server. The Executor measures, executes and commits, within the scope of a Mission or of an Owner's prompt traced by an execution Note, and never decides the architecture ([CONTEXT.md](../../CONTEXT.md)). A session determines its role at opening through three rungs: a startup hook if one injects a role, then a capability probe ("can I execute a shell command?" yes means Executor, no means Pilot), then the declaration in the Mission's mini-prompt. On a contradiction the session stops and asks you; on doubt, Pilot, the least powerful role, is presumed.
